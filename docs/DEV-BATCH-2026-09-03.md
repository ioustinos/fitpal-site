### A2 · WEC-678 — payment link amounts *(Urgent)*

Three defects, one symptom. Reported on order FP-260813-00001.

* **Server:** `netlify/lib/viva/createOrder.ts:71` rejects any amount that isn't exactly `order.total`. That guard is a relic — the endpoint, the Viva call, `payment_links.amount`, `verify.ts` and `markPaid.ts` were all built for partial amounts by WEC-606/607. Relaxing it is the whole fix. `submit-order.ts:1166` passes the full total, so the customer flow is unaffected.
* **Client:** `src/admin/pages/Orders.tsx:1657` seeds the amount input with a `useState` initialiser that never re-syncs. Edit the order with the drawer open and the label updates while the input keeps its mount-time value.
* **Checkbox:** "Charge more than the remaining balance" is client-side only. Plumb it to the server or delete it.
* **Plus the hole:** an outstanding link keeps its frozen amount after the order total drops. Void or flag it.

**Same person as A3** — both concern a payment link outliving the order state.

### A3 · WEC-681 — cancelling at Viva leaves a phantom order *(High)*

Card → Viva → **Cancel** → back → retry with bank transfer = **two complete orders**, both with 5 child_orders and 8 items, 2 minutes apart (FP-260827-00001 card, 00002 transfer).

`submit-order.ts` must promote the draft before redirecting, because Viva needs an `orderId` as `merchantTrns`. But `OrderReturn.tsx:71-72` does **nothing server-side** on the failure return — no cancel, no revert, no clearing of the client `draftId`. The retry can't reuse the row (promote is guarded `WHERE status='draft'`, and it is now `pending`), so a second order is created. `viva-reconcile` only sweeps these after **48h**.

Three phantoms are live right now, €87.70.

**Recommended fix:** carry our own `orderId` across the redirect; on landing at `/order/pending/failure`, call an endpoint that **reverts that order to `status='draft'`** (guarded on ownership + `payment_status='pending'`). Reverting rather than cancelling means the retry promotes the *same* row — one order, right method, no duplicate, order number reused. Also void the associated `payment_links` row so a stale link can't be paid later.

Do not depend on Viva's return params — a cancel arrives with no `t`, which is exactly why the page can't identify the order today.

✅ **Airtable and the kitchen are NOT affected** — `pushOrder.ts:43-47` already refuses to mirror card+unpaid. Do not "fix" that guard.

❓ Check whether the customer's own account page lists the abandoned order.
